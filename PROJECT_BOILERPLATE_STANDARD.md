# AIX Agent Project Boilerplate Standard

## Purpose

Use this document as the mandatory architecture standard when creating or rebuilding any
enterprise AI-agent project. Product behavior may change by use case, but the module boundaries,
initialization sequence, configuration approach, safety controls, tests, and deployment structure
defined here must remain consistent.

This standard is implementation guidance. Project-specific requirements, approved platform
libraries, security policies, and authoritative source material take precedence when they impose
stricter controls.

## Instructions for an implementation agent

Build the requested application using this repository as the boilerplate reference. First inspect
the existing reference files and create a mapping between the new use case and each boilerplate
module. Preserve the architecture and lifecycle; adapt business names, prompts, knowledge,
schemas, tools, API models, tests, and deployment values without collapsing module boundaries.

Do not copy secrets, customer records, generated caches, local virtual environments, or developer
`.env` files. Do not invent unavailable enterprise APIs or claim that mocked integrations are live.
Record assumptions and clearly identify synthetic or placeholder data.

## Module responsibilities

### `agent/main.py`

- Define the FastAPI application and typed Pydantic API contracts.
- Attach the application lifespan from `agent.initialize`.
- Provide liveness and readiness endpoints.
- Add request IDs, timing, controlled errors, and approved CORS behavior.
- Keep route handlers thin; move business processing to domain services or tools.
- Never expose credentials, stack traces, provider payloads, private prompts, or connection strings.

### `agent/initialize.py`

Initialize components in this order:

1. Load environment variables.
2. Select environment-specific configuration.
3. Initialize logging and settings.
4. Initialize embeddings and document storage.
5. Seed or reconcile approved knowledge when enabled.
6. Build the LangGraph graph through `GraphFactory.create()`.
7. Mark the application ready only after required dependencies are healthy.

During shutdown, cancel background tasks and close checkpointers, database pools, document stores,
telemetry clients, and other resources safely.

### `agent/graph.py`

- Provide an asynchronous `build()` function.
- Use LangGraph `StateGraph` with explicit nodes and routing.
- Initialize the model from `LLM_MODEL_KEY`.
- Obtain the checkpointer through `get_checkpointer()`.
- Apply logging and timing middleware before binding tools.
- Include a supervisor node and a `ToolNode` when tools are present.
- Use conditional tool routing and compile with the configured checkpointer.
- Keep generated-file warnings when the graph is generated by an assembler.

### `agent/factory.py`

`GraphFactory.create()` must be the public construction boundary and delegate graph assembly to
`agent.graph.build()`.

### `agent/checkpointing.py`

Support configuration-based selection at minimum:

- `memory` for local development and unit tests;
- `postgres` for durable environments.

Use the API session identifier as the LangGraph `thread_id`. Do not silently fall back from a
requested production checkpointer when doing so could hide a deployment problem.

### `agent/model.py` and `agent/providers.py`

- Isolate vendor and enterprise SDK imports behind narrow adapters.
- Prefer the approved enterprise `amodel(...)` integration when available.
- Permit deterministic local substitutes only for development and unit testing.
- Clearly label fallback responses and synthetic behavior.
- Never report a fallback as a successful connection to a real provider.

### `agent/middleware.py`

- Emit structured operational logs.
- Include request/session correlation without logging secrets or excessive personal data.
- Measure model and tool execution time.
- Keep middleware independent of business-domain rules.

### `agent/rag/`

- `prompt.py`: domain-aware retrieval instructions and grounding rules.
- `settings.py`: immutable, validated RAG configuration loaded from environment variables.
- `initializer.py`: embedding and document-store initialization on `app.state`.
- `tools.py`: asynchronous LangChain tools for retrieval.

RAG tools must support multiple subqueries, asynchronous embeddings, retrieval limits, score
thresholds, metadata filters, safe content normalization, partial-query failure, and debug logging
behind `DEBUG_MODE`.

### `config/`

- Keep constants, prompt composition, settings, and environment loading separate.
- Select SafeChain configuration by environment.
- Validate required production configuration during startup.
- Use this precedence without overwriting an existing value:
  1. Process environment
  2. Mounted secrets file
  3. Local `.env`

### `knowledge/`

- Organize approved documents by domain or access-controlled collection.
- Store only non-secret, repository-approved material.
- Label synthetic examples, drafts, and SME-review templates.
- Preserve source metadata and stable document identifiers.
- Make ingestion idempotent and reconcile removed or superseded documents.
- Enforce metadata filters and user authorization before returning content.

## Data and retrieval architecture

Use PostgreSQL with pgvector as the default persistent knowledge store unless the approved project
architecture specifies another implementation. Store chunk content, stable IDs, source metadata,
content hashes, embeddings, timestamps, access metadata, and domain filters. Create schema and
indexes idempotently.

Retrieval should follow this flow:

```text
request
  -> authorization and validation
  -> subquery generation
  -> embedding generation
  -> metadata-filtered vector retrieval
  -> score filtering and optional reranking
  -> context construction
  -> LangGraph/model execution
  -> grounded response with sources
```

Missing knowledge must produce an honest low-confidence response or clarification request, not an
invented answer.

## API conventions

Every project must provide:

```text
GET  /api/v1/health/live
GET  /api/v1/health/ready
POST /api/v1/index
POST /api/v1/retrieve
POST /api/v1/chat
```

Add domain endpoints when structured inputs or outputs provide better safety than free-form chat.
Use typed request and response models, explicit field validation, stable versioned paths, request
IDs, safe error responses, and source attribution.

The chat contract should include a query plus optional user and session identifiers. Resolve
missing identifiers safely and use `session_id` as the graph thread ID. Do not accept a response
object as a chat request.

## Domain adaptation checklist

Before implementation, document:

- Product goal, users, decisions, and measurable outcomes.
- Authoritative knowledge sources and data owners.
- Domain vocabulary and API contracts.
- Required metadata filters and authorization rules.
- External systems, approved authentication, and rate limits.
- Human-approval boundaries and prohibited actions.
- Failure behavior, fallback behavior, and escalation paths.
- Evaluation dataset, expected answers, and acceptance thresholds.

Map each requirement to one or more modules before modifying code. Business logic belongs in new
domain services, prompts, knowledge, tools, and endpoints; infrastructure concerns stay in the
boilerplate modules.

## Testing requirements

Unit tests must be deterministic and must mock enterprise network services. Cover:

- Environment precedence and settings validation.
- Memory and PostgreSQL checkpointer selection.
- Embedding and document-store initialization.
- Knowledge chunking and idempotent indexing.
- Query embedding, filters, thresholds, and empty results.
- Multi-query partial failure.
- Prompt composition, tool binding, and graph routing.
- Session/thread continuity.
- Request and model timing middleware.
- Liveness and readiness.
- Indexing, retrieval, chat, and every domain endpoint.
- Grounding and source attribution.
- Provider failures and safe client-facing errors.
- Authorization and data-leakage boundaries.

Mark tests requiring live databases, models, observability, or external systems as integration
tests. They must not run as ordinary unit tests without explicit configuration.

## Deployment requirements

- Local startup through `scripts/start_local.sh`.
- Container startup through `scripts/start_docker.sh`.
- A production-compatible Gunicorn/Uvicorn entry point.
- A non-root, minimal Docker image where platform rules allow it.
- Helm values, schema, application deployment, service, and networking templates.
- Health probes aligned with the FastAPI endpoints.
- CI checks for formatting, linting, typing, tests, image build, and chart validation.
- Secrets supplied only through the approved runtime mechanism.
- Placeholders for organization-specific registries or repositories when values are unknown.

## Required verification gates

Do not declare a project complete until applicable gates pass:

1. Format, lint, and type checks pass.
2. Unit tests pass without live enterprise dependencies.
3. Application starts locally.
4. Liveness and readiness return success.
5. Approved knowledge is indexed and retrievable.
6. Representative grounded requests return correct sources.
7. Same-session requests preserve expected graph state.
8. Failure responses do not leak internal information.
9. Docker image builds.
10. Helm templates validate.
11. No credentials or local artifacts are staged in Git.
12. README documents setup, configuration, APIs, testing, and known limitations.

If an enterprise dependency, credential, or source is unavailable, report that limitation and the
mock or adapter used. Do not describe an untested integration as complete.

## Definition of done

A project conforms to this boilerplate when it preserves the required structure and initialization
flow, implements its domain through explicit adapters and typed contracts, grounds AI outputs in
authorized sources, keeps humans in control of consequential actions, passes the verification
gates, contains no secrets, and documents every unavoidable deviation from this standard.
